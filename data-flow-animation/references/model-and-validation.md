# 数据模型与验证

在分析源码、建立逐步模型和设计验证场景时使用本参考。以下字段是建模建议，不要求项目照搬名称或框架。

## 变量账本

每个对象以稳定 ID 连接代码、布局和动画；同名变量在不同 rank / 核上必须可区分。

通信场景默认至少四个 rank。把队列键定义为“发送者、接收者、QP”等完整身份，通知键定义为“接收者、来源、QP”；不能沿用两卡场景的 `1-rank`。本机路径、零数据对端和异步完成也要由模型计算。

| 字段 | 应记录的信息 |
|---|---|
| 身份 | 对象 ID、源码变量名、定义或绑定位置 |
| 归属 | rank、物理核 / 逻辑核、线程或共享作用域 |
| 存储 | 内存层级、基址符号、别名、dtype 与实际位模式解释 |
| 大小 | 逻辑 shape、有效元素数、有效字节数、实际分配字节、对齐填充 |
| 寻址 | 多维索引到线性索引，再到字节偏移的公式 |
| 生命周期 | 初始化、写入、可读条件、复用、释放 / Reset、历史快照 |

不要混淆全局专家 ID 与本地专家 ID、来源 rank 与目的 rank、逻辑核编号与物理核编号。数组分配得大，不意味着所有元素都有效；每核读取完整输入，也不意味着输入已经按核切分。

可见数字另建释义清单：字段名、类别、单位、公式或源码来源、教学选择依据。例如“token 编号 0”与“首元素值 1”必须分栏；`F=[1,0]` 只有在说明每个位置对应的块、1/0 的状态含义后才能使用。优先直接写字段，不依赖悬浮提示或藏在长文档里的解释。

用 `S_dst + index × recordBytes` 一类符号表达地址，图中注明单位。若一个记录同时存 ready 和 count，展示各字段及填充；清 ready 时不得把仍保留的 count 误画成零。

## 步骤与事件

推荐让纯模型输出下列概念，再由两个页面渲染。寻址和数学计算不要分别写在两个渲染器里。

| 概念 | 用途 |
|---|---|
| `sourceRef` | 固定提交、文件、真实行号及本路径适用的代码行 |
| `stageId / stepId / batchId` | 稳定标识阶段、教学帧与循环批次 |
| `actors` | 本批参加的 rank、核、线程与任务范围 |
| `reads / writes` | 对象 ID、索引区间、访问值、实际执行条件 |
| `transfers` | 源对象、目的对象、偏移、载荷、提交与完成状态 |
| `waits / dependencies` | 等待标志、等待范围、前置事件及完成条件 |
| `snapshot` | 当前帧各对象状态；区分实时内容与历史快照 |
| `activeCodeLines` | 根据当前实际分支确定的源码重点集合 |

每帧至少能够回答：“R0 的哪个核，执行哪条命令，读了哪个变量的哪几格，写到 R1 的哪个对象，本步哪些动作并行？”解释中先给具体例子，再给通用公式。

随机示例使用固定种子或直接保存输入；任意拖动进度必须能够重建同一帧，不依赖此前是否完整播放过。可以预计算快照，也可以从初始状态确定性重放；根据数据规模选择。

## 并行与异步的表达

1. 把参与者并排放在 rank / 核泳道中；同批可并行活动同时出现，不用轮流播放造成“各 rank 串行工作”的误解。
2. 同一核内循环可按迭代展开。多条异步操作顺序提交后统一等待时，展示“已提交”与“已完成”的区别。
3. 数据需要经特定同步才能被读取时，显示依赖或等待标志；不要把一个局部流水同步画成全 rank 屏障。
4. 不同核 / rank 的相同循环编号可合并为教学批次，但必须说明真实执行可能错开。只有 trace 证据才能支持真实重叠时间与时延。
5. 元数据 ready 与实际 payload ready 分开。计数通信完成不能推导 token 已到达。
6. 内存复用后的旧 UB 内容只能作为标明时刻的历史快照，不能继续显示为当前有效数据。

遇到指针重解释、浮点视图处理整数位模式等实现，分别解释存储类型和运算语义。不能默认为数值类型转换；未验证的舍入、溢出或硬件特殊行为应保留为模型边界。

## 有意义的验证

根据算法选择不变量，避免只检查页面里出现了某个字符串。

| 场景 | 验证重点 |
|---|---|
| scatter / dispatch | 每个输入记录的目的索引正确，载荷与元数据分别满足各自守恒关系 |
| count / prefix | 总计数正确；包含式前缀的逆差分等于输入；排他式前缀按实际定义检查 |
| 多核前缀 | 每核起始偏移等于前面核的小计之和，各核输出拼接后等于串行参考 |
| 输出区间 | 起止索引、空区间、覆盖范围和是否允许重叠符合源码 |
| 全零 / 空输入 | 实际合法输入范围内，零值写入、ready、分支和后续状态均正确 |
| 集中 / 不均匀 | 单一目的、余数分工、空任务核、不同核长度的批次边界正确 |
| 发布 / 消费 | 输出副本数量、归属、等待条件、清旗和生命周期正确 |

数学模型通过仅证明已编码的语义和假设一致；不等于硬件内核精度、性能或通信可见性已实测。

源码映射应分开保存：所属函数、定义行、调用链、连续上下文区间、实际执行行。验证区间中的原文逐行一致，函数定义确实包含该函数名，活动行落在展示区间内，失败分支不高亮成功返回。多 rank 扩展时重新核对核数分工、发送核编号和原子取号偏移。

## 布局和行为验收记录

记录实际执行的组合：页面 × 视口 × 阶段 × 关键预设。除了根页面，还检查代码容器、数组容器、说明区与图例的内容边界；`overflow: hidden` 可能隐藏失败。比较内容尺寸与扣除内边距后的可用区域，并实际查看最拥挤的画面，不能只靠尺寸脚本判断可读性。

行为验收覆盖双页进度、拖动后继续播放、运行至终点、暂停后刷新、后加入、控制权切换、会话隔离与选中记录的来源追踪。交付时区分已实测、仅模型验证和未验证项目。

无滚动、无越界并不能证明无遮挡。把几何相交检测、文字与徽标边界、连线覆盖文字、白色背景 computed style 与实际 CSS 视口加入记录，具体方法见 [教学与视觉验收](teaching-and-visual-acceptance.md)。
