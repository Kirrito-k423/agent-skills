# 专项诊断协议

仅在遇到对应问题时读取并执行本文件。所有结果归档到当前 Goal 的过程目录。

## 版本兼容性

禁止通过连续升降级碰运气。切换前建立兼容性矩阵：

| 组件 | 当前版本 | 要求/接口 | 证据来源 | 候选版本 | 风险 | 结果 |
|---|---|---|---|---|---|---|
| Python | | | | | | |
| 框架/运行时 | | | | | | |
| 加速器插件/驱动 | | | | | | |
| 编译或通信库 | | | | | | |
| 模型/推理后端 | | | | | | |

候选版本必须至少有一种依据：

- 仓库 lock/requirements、Dockerfile 或 CI；
- 官方兼容表、发布说明或示例脚本；
- 已知成功镜像/环境；
- 相邻实现使用的组合；
- 已定位的 API/ABI 变更。

每次只切换一个主要版本变量，并记录旧环境恢复方法。没有新增依据时最多尝试两个候选；之后停止版本轮盘，转代码调查、最小复现或升级。

## OOM 与资源不足

先把 OOM 定位到阶段，不接受笼统的“训练 OOM”：

```text
权重加载 | rollout | KV cache | logprob | reward
backward | optimizer step | 通信临时 buffer | checkpoint
```

每次记录：

- 最后成功阶段、首个失败位置和每 rank 时间线；
- 每 rank 峰值 allocated/reserved/空闲量；
- 模型层数、参数量、dtype 和是否保留双份权重；
- micro/global batch、prompt/response 长度、rollout 数；
- DP/TP/PP/CP/FSDP/ZeRO 等并行与分片设置；
- activation checkpoint、optimizer state、KV cache；
- 失败前后的内存增量和通信临时区；
- 运行编号、配置快照和完整错误签名。

任何减层、减 batch、缩短序列或改变并行方式前，先回答：

1. 预计减少哪一类内存？
2. 为什么与当前失败阶段相关？
3. 预计减少多少或至少什么数量级？
4. 哪个观察结果能证明判断正确？

若没有内存组成和阶段证据，先加采样点或做最小加载/forward/backward，不开始全量调参。证明确属物理下限时，给出资源需求或范围选择并升级，不无限减配。

## 隐蔽故障增量维测

当现有日志不足以一眼区分候选原因时，每轮只增加一小步维测：

1. 围绕报错前后最近的稳定边界选择 2–4 个观测点。
2. 使用 `TSJDEBUG` 或项目约定的环境变量控制，默认关闭。
3. 日志文件名至少包含时间戳、run id、rank id 和 pid：

   ```text
   goal_process/<goal-id>/runs/<timestamp>-C<nnn>/
   tsjdebug-<run>-rank<rank>-pid<pid>.log
   ```

4. 记录阶段进入/退出、关键 shape/dtype/device、内存、分支条件和异常前最后成功点。
5. 不记录完整训练数据、密钥、token 或个人敏感信息；大 tensor 只记录统计量和有限样本。
6. 保持维测改动可独立回滚，必要时用单独提交或 patch 保存。
7. 新日志回来后先更新事实和假设，再决定下一处观测；禁止同时大改业务逻辑。
8. 当证据足以区分原因时停止加日志，给出根因、证据链、修复方案和验证方法。

推荐的单轮目标写法：

```text
本轮目标：
确认故障发生在 <阶段 A> 之前还是 <阶段 B> 之后。

本轮动作：
在 <观测点 1/2/3> 增加受 TSJDEBUG 控制的分 rank 日志。

结束条件：
获得能够排除至少一个候选原因的时间线、状态或资源数据。
```

## 分布式故障

- 为每条日志补充 rank、local rank、world size、host、pid 和阶段。
- 区分首发 rank 与连带失败 rank，不用最后打印的异常代替根因。
- 记录 collective 前后、shape/dtype/device、参与 rank 和超时。
- 先用最少 rank/最小数据复现，再扩大规模。
- 时钟可能不一致时使用单调序号或事件标识关联日志。
- 任何“某 rank 卡死”的结论都必须有其最后成功事件和其他 rank 的等待位置。
