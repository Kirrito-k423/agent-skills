# 验证协议

在制定验收、运行对比或报告性能结论时阅读。使每项验证直接对应候选改变的算法、并行机制或计时口径，避免为形式堆积检查。

## 固定比较对象

记录原始基线、候选和输入生成方法的版本或文件哈希，保留未提交差异。记录硬件型号、设备数、运行时/编译器版本、优化标志、相关线程数及实际可用资源；配置中不收集或输出凭据。

同时涉及算法和并行化时，尽量保留三个对照：

1. 原始实现：衡量交付对现有业务的收益。
2. 合理的优化串行实现：判断收益是否主要来自减少重复工作。
3. 并行候选：判断额外并行的净收益及适用规模。

可以按需求选择更多机制消融，不把每个组合都变成必跑任务。基线与候选使用相同合法精度、输出要求、工作负载和资源口径；单独注明候选额外资源。

## 正确性

- **输出契约：** 检查尺寸、内容、顺序、数值误差及副作用。精确整数按约定检查溢出；浮点说明绝对/相对容差、非有限值与确定性要求，不擅自放宽原始契约。
- **边界与分布：** 根据改动选择空输入、最小规模、非整块尾部、跨分块边界、重复值、极端数值、热点倾斜和任务数少于工作线程等用例。
- **并发契约：** 检查每个任务的唯一所有者、完成次数、生产后发布、消费前可见、缓冲回收、终止与进度。对取消屏障或引入异步的改动，验证单项就绪协议与结果完整性。
- **循环同步改写：** 覆盖零轮、单轮、不整批尾部、窗口回绕和跨轮缓冲复用；按机制加入生产者延迟、完成乱序和有界队列接近容量的情形，核对没有提前读取/覆盖、漏等、重复消费或无法推进。外提操作需保持零轮路径与异常语义。
- **复用契约：** 连续调用并改变输入，检查缓存失效、陈旧数据、跨请求污染、池退出和内存增长。
- **相关工具：** 在支持的目标上按需用 sanitizer、竞态检查、设备检查或多 rank 验证。工具通过是支持证据，不是并发正确性的完备证明；主机检查也不覆盖设备内存模型。

有正确性失败时报告失败输入和根因范围，不能把该候选更快的数字认定为可用收益。

## 计时边界

| 指标 | 起止与纳入内容 | 常见误判 |
|---|---|---|
| 单次延迟 | 请求进入到约定结果可用 | 只计提交、排除排队或必要拷贝 |
| 内核局部时间 | 在设备时钟或已正确连接的事件上覆盖目标工作完成 | 用主机 API 返回时间代替设备执行时间 |
| 稳态吞吐 | 稳态窗口内有效完成工作数 / 墙钟时间 | 把提交数当完成数；积压持续增长仍称可持续吞吐 |
| 冷启动 | 按应用路径计入首次创建池、分配、编译和装载 | 将预热排除后的数据描述为首次响应 |
| 尾延迟 | 在注明并发、到达方式及负载下统计单请求延迟 | 只记录批平均值；样本太少仍给稳定 p99 |

异步设备操作使用官方支持的事件或同步计时。多 stream/多核任务应建立覆盖所有相关完成事件的依赖，外层计时只纳入目标范围；为局部测试加的同步不能悄悄破坏原生产流水。[CUDA 官方计时说明](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#timing) 提供异步计时的例子，其他设备需使用其自身 API。

不同设备或不同 rank 的本地时间戳不能直接相减解释物理延迟，除非证明时钟已校准。多 rank 完成时间需要覆盖所有必要参与者；平均 rank 耗时会掩盖拖尾。

内核诊断尽量缓冲采集后统一导出；记录插桩成本，以关闭诊断的构建测正式收益。日志打印和每任务额外全局同步不应污染热路径。

## 有界实验

1. **确定工作集。** 从实际输入选择小规模、常用规模及接近资源边界的代表规模；涉及不均衡时加入真实倾斜分布。不要用未获授权的大规模负载扩展测试范围。
2. **核实机器状态。** 记录可用核/卡、竞争负载及影响结果的功耗或频率状态；不擅自停止其他任务或修改系统策略。
3. **分开预热。** 将编译、缓存、池启动的预热样本与稳态样本分开保存；若业务包含冷启动，另做相应测量。
4. **配对比较。** 交错或随机化基线与候选顺序，采用相同输入序列；重复到能够判断收益与波动，遵守预算。不要把重复次数机械固定为任意一个数。
5. **扫描资源和粒度。** 采用代表性的工作线程数、批大小或块大小；记录何时开始平台期或退化。线程池与底层库线程数需同时核实，避免嵌套并行掩盖真实占用。
6. **统计结果。** 保存原始样本、样本数、中位数与离散程度；尾延迟需要足量单请求样本。置信区间若使用重采样，应说明样本单位和相关性处理。数据不足时标记，不给虚假精度。
7. **核对端到端。** 记录有效输出数、失败/丢弃数、排队情况、内存峰值及资源增长。核对局部收益是否转化为应用收益，说明批处理的等待成本。

对吞吐测试说明开放到达或封闭并发的负载模型。超载时主动报告队列增长、失败率和尾延迟，不能仅靠增加积压提高“吞吐”。

## 计算与归因

```text
延迟加速比 = 同口径基线延迟 / 候选延迟
延迟降幅 = 1 - 候选延迟 / 基线延迟
吞吐提升 = 候选有效吞吐 / 基线有效吞吐 - 1
同一算法的 P 路并行效率 = 单执行单元时间 / (P × P 路执行时间)
```

分别计算 p50/p95/p99 的变化，不用中位数的收益代表尾延迟。比较多个输入时保留分项结果及业务权重，不能用未说明权重的平均值掩盖回归。算法改变时，相对原始实现的加速比不能冒称硬件并行效率。

每个机制结论连接到对应证据：例如工作计数下降支撑去冗余，时间线重叠支撑流水，资源扫描支撑并行扩展；仅观察耗时变化时把原因表述为待验证假设。

对热循环改写，比较每轮操作数、等待/查询次数、必要屏障次数、阻塞时长和端到端时间，并注明实测或估算。同时涉及不变量外提与等待位置/范围变化时，分开验证两者的收益来源；若只把等待移到循环外，计时仍须包含最终完成和结果可用。检查批量化是否把开销转为首项等待、尾延迟或额外缓冲，不能仅凭循环体变短认定优化成功。

## 验收状态

| 状态 | 使用条件 |
|---|---|
| 目标已验证 | 目标环境中约定的正确性与性能比较均完成，结果支持主目标且满足约定约束 |
| 部分验证 | 仅部分输入、局部基准或主机检查完成，列出未覆盖范围 |
| 仅分析 | 只有源码推导或设计建议，无对应运行证据 |
| 未达标 | 正确性失败，或测量明确违反约定指标/约束；没有硬阈值而仅相对基线变慢时写“相对该基线退化”，不据此判定原代码违反业务要求 |
| 收益不明确 | 波动足以解释差异，或样本与计时证据不足以判定性能方向 |

状态附在具体候选和工作负载上。没有 GPU/NPU 或多机环境、但目标工具链和接口已知时，提供可重跑的目标环境验证命令或最小驱动；未实际执行的命令明确标注。目标芯片、版本或接口仍未知时，交付最少待补信息、可复用契约测试及下一项验证方案，明确设备入口未完成，不虚构命令。达到本次可执行范围后交付，不反复重跑无关检查。
