# 华为技术汇报

## 本地默认交付

这是本用户后续技术汇报 PPT 的默认 Skill。沿用已选择的技术项目版式：红色标题、**红底白字的“分析结论”正方形标签**、右侧通栏浅灰结论块、黑灰正文、原生可编辑表格及逻辑图。正方形边长等于结论区高度，白字居中分成“分析”“结论”两行、每行两字；PPTX 使用可编辑的原生形状。用户指定其他风格或模板时优先遵从。

**封面与 Thanks 页优先直接复用用户模板。** 本用户默认使用已授权保存的浅色 16:9 模板，保留背景图、母版、布局和原生元素。封面填入已确认作者“谭邵杰 t00906153”与版本日期，用户本次给出的作者或模板优先覆盖。未提供部门或安全级别时移除空字段。最后追加模板原始 Thanks 页并计入总页数。实际复用接口与授权模板见 [模板封面与结束页](references/template-bookends.md)。

**完整汇报默认顺序为独立封面、第一章目录、第一章正文，随后在每次一级章节切换前重复展示完整目录。** 当前章节用红色加粗，已经讲过的章节标题、编号和页码变为灰色，后续章节保持深灰。各次目录的章节顺序与实际页码一致，页码包含新增目录页。总览或摘要内容页不能代替封面，也不能省略目录。封面和目录不套正文结论栏，不添加虚构作者、部门、日期或成果。用户要求单页、局部修改、只生成正文或固定总页数时，按明确范围处理；固定页数应先为章节目录预留位置。

## 整理既有草稿：逐页保留与积极用图

- **先逐页建立对应表，再整理。** 记录每页的主题、结论、问题、图表、条件、数据与其在新稿中的页码。默认保留原稿每一页及其独立信息，新稿总页数不少于原稿；允许按汇报逻辑调整顺序、拆页和增加导航。原有空白占位页或配色示例保留为标注清楚的占位页或附页。仅当用户明确授权精简、删除或限定较少页数时，按其范围处理。
- **保留问题及推导链。** 原稿中的问题编号、疑惑、备选解释、假设、修正方案和结果均要有对应页面。按“目标图与目标 → 现象 → 问题 → 原因或假设 → 应对方案 → 结果”组织，避免把推测写成事实；有尚未确定的内容时，可直接在 PPT 中列“待确认”的具体问题，不要为消除疑问而删页或编造答案。用户指定最终结果放在最后时遵循该顺序。
- **按页面要回答的问题选图表。** 复现目标图靠前；趋势、对比、机制等关键证据优先使用与本页结论直接相关的曲线或结构图，可裁切、拆页或按已知数据重绘。若表格更直接回答问题，就用可编辑表格。纯文字或表格截图、信息量低或与本页结论无关的图，应提取其有效事实、数值、单位和必要条件，融入原生文字或表格；不得为保留图片而牺牲关联性，也不得丢失有用信息。未知或相互矛盾的数据保留具体待确认项。
- **实验图旁直接标注实验配置。** 每张实测性能图或表的附近，用投影可读、可编辑的文字标出模型、设备型号与数量、推理并行方式、每卡 HBM 中的 KV 配置；再按需补充输出长度、样本或其他影响比较的条件。配置需要与具体图和数据一一对应，不能只藏在原图小字、其他页面或备注中。区分引擎自动计算的可用 KV 预算和手动固定 KV 池；缺失项标“未记录/待核对”，不猜测，参考目标图须保留其自身条件。
- **用直接、准确的中文表达。** 参照 `anti-defensive-writing`：标题和结论先说结果、价值及判断，删除重复的免责声明、自我贬低和叠加保留词；保留决定结论成立的前提、真实不确定性及不利结果，不把相关写成因果。新增图的标题、节点、图例、轴名及边注默认使用中文，KV、QPS、TTFT 等常用技术缩写和符号保留；外文原图可保持原貌，用户指定其他语言时优先。
- **交付前对照。** 用实际页码核对原稿与新稿的逐页映射、图和问题清单，并按 `source_draft` 可选校验合同检查页数、映射及关键图片/问题编号；该静态检查不替代人工语义和视觉核验。来源图仍为图片时，如实说明可编辑范围。

渲染器为多页汇报默认补齐封面和目录；通过 `frontmatter` 提供副标题、日期与章节范围。有明确 `chapters` 时默认按章重复目录，显式 `repeat_agenda: false` 可用于用户要求的单次总目录。未划分章节的短稿保留一次逐页总目录。局部页面或既有正文回放显式设置 `include_frontmatter: false`。论文报告继续使用原有逐章高亮目录，不重复补齐。字段、计数与来源说明见 [完整汇报](references/complete-report.md)。

## 按用途进入两个分支

用户指定优先；未指定时综合汇报目的、读者要做的决定和材料内容判断。不能只看文件名或某个关键词。

| 分支 | 典型用途 | 页面表达 |
|---|---|---|
| 技术项目 `technical-project` | PDCP/TDR、立项、技术规划、目标和进展、交付评审 | 项目单专题用挑战＋目标或目标＋进展；特性实现分析用可多行的分析结论；多专题按技术布局/总进展组织 |
| 洞察分析 `insight-analysis` | 模型/特性原理、版本差异、性能和资源、硬件亲和性 | 每个内容页显式保留红色“分析结论”标签＋通栏浅灰结论块 |

PCP/DCP 是技术名称，不等于 PDCP。模型主题也能做项目评审；项目材料也能包含原理图。全篇用途决定主分支，具体页按问题选图表，不因局部内容切换分支。

技术项目分支中的模型/特性原理与实现分析，默认使用 `header_mode: "conclusion"`：每页以具体判断、源码机制和实际影响组成分析结论，可用多段表达，不强套挑战/目标。结论须体现自己的分析，但不能把推断、代码存在或测试文件存在写成实测结果；普通项目规划和进展页仍可使用成对摘要。用户指定优先。

`python scripts/ppt.py route request.json` 辅助判断，支持显式风格、目的及材料摘要。证据不足返回 `needs-context`；结合已有对话判断，只有仍影响选型时才询问用途。

- 技术项目：读 [technical-project-style.md](references/technical-project-style.md)。正式版布局提炼见 [project-report-reference.md](references/project-report-reference.md)。
- 洞察分析：读 [insight-analysis-style.md](references/insight-analysis-style.md)。需要计算时再读 [model-insight-workflow.md](references/model-insight-workflow.md)；用户确认的基准直接沿用。
- 论文分析/汇报仍属洞察分析：按 [论文报告](references/paper-analysis-report.md) 使用 PDCP 风格封面、逐章重复且高亮当前章的完整目录，再讲核心创新、设计机制和实验结果。可用 `scripts/paper_report.py` 组装，封面和目录不套正文结论栏。

## 制作

新绘图的标题、节点、连线、图例、坐标轴和边注默认使用中文；技术缩写、公式与专有名称按习惯保留。外文原图中的文字与语言可以直接保留，用户指定其他语言时优先。绘图直接交付二维图像，布局按本次内容选择。

模型结构图优先基于匹配版本的 vLLM-Ascend 实际执行路径；继承部分继续查对应 vLLM。没有对应实现时，用 Hugging Face 源码或用户提供的结构/实现材料绘制，并说明原理与运行实现的边界。用户已确认的数据与版本约束继续沿用。图中体现关键融合算子和必要的 shape 变化，不套用其他模型的内核或维度。

特性图沿用同一二维绘图标准，以 vLLM-Ascend 的实际实现为依据，代入目标模型及配置，讲清计算、通信和状态如何流动；继承或委托上游的部分继续核对匹配的 vLLM。HF 原理不能代替 Ascend 特性实现证据，未找到实现就标明范围，见 [特性图](references/runtime-static-analysis.md#特性图)。

涉及模型的特性汇报，首个内容页将模型主干与特性新增步骤结合：从实际受影响模块连出阶段/条件路径，区分已有计算、新增或替换的算子、通信与合并，并配启用前后对照表给出具体结论。混合模块不套用同一条通信链。按 [特性首页规则与组件](references/feature-backbone-overview.md) 制作；原图优先与两个风格分支的要求不变。

1. 用 `plan` 读取本次分支、适用规则和最小组件；先理解材料的核心变化、实现约束和证据，再形成判断与组织页面。洞察结论按 [结论写法](references/insight-conclusions.md) 提炼关键事实、原因和具体判断，不能只摘抄数字或复述页题。已有结构化材料优先复用。
2. 技术项目先查用户材料、对应版本的仓库文档（含 `docs` 图片）和官方论文，选择能直接回答本页问题的图、表或原生文字；匹配且信息丰富的原图可本地复用。先按 [图表取舍](references/technical-project-style.md#原图优先) 核对版本与内容。需要新绘或改绘时再选组件：`assets/units/catalog.json` 是最小单元目录，`plan` 返回 `component_builders`；通过 `scripts/diagram_components.py` 实际实例化所需组件，保留参数、端口和使用记录，不能只在备注中写组件名称。新结构可扩展局部组件，不强套现有拓扑。见 [组件复用与绘图验收](references/component-reuse-and-review.md)。按问题选简单曲线、柱状图、对比表及必要的结构图，见 [chart-selection.md](references/chart-selection.md)。
3. 新绘图继续沿用 [reference-diagram-fidelity.md](references/reference-diagram-fidelity.md)，模型结构也可使用 [二维结构图组件](references/model-diagram-renderer.md)：完整主干、实际分支、缓存与回路。昇腾运行图先走读实际 Ascend 调用链，体现关键融合算子、启用条件及必要的 shape 变化，见 [执行实现与 shape](references/runtime-static-analysis.md#把实现画进模型结构)。新绘图内文字与批注黑灰红、低饱和填充，不能退化为无关联的方框卡片。原图保留技术内容、拓扑和原有语言；新增标注遵守黑灰红规范。
4. 用同一份 `deck-model.json` 生成 HTML，原图用 `image` 本地嵌入并保持比例；技术项目按图形密度选概览配表、图表核验或原图通栏，可点击放大。局部版式见 [技术项目风格](references/technical-project-style.md#原图和分析怎么搭配)。新绘图同步生成 SVG、draw.io，不把原图声称为可编辑图源。接口见 [runtime-contract.md](references/runtime-contract.md)。`python scripts/ppt.py render request.json output/`。逻辑画布1280×720，HTML自包含并自动适配。图表、说明和页数随内容变通，不强塞固定页数或重复卡片。
5. 使用 `diagram` 数据接口的新结构图设置 `diagram_contract: 1`，声明实际存在的主路径、共享分支与缓存读写；`validate` 校验组件重放和这些路径，`render` 保存 `diagram-audit.json`。使用二维 `Scene` 组件时单独保存场景、图源、`audit` 及源码语义核对记录，不将图片嵌入检查当作连线验收。原图检查来源、适用版本、清晰度、比例和关键内容完整性，不要求组件重放。再逐页检查字体、连线遮挡、留白、翻页及图的解释力。保存实际查看者和截图摘要；静态通过不能记成视觉通过或用户确认。
6. 明确需要可编辑 PPTX 时先读 [Codex 原生 PPTX](references/native-pptx-codex.md)，保留原生文字/表格/形状和备注，逐页渲染检查。已有 PPTX 任务的后续修改继续交付 PPTX，并保持 HTML 与其来自同一份数据。其他任务默认交付 HTML。

共享要求见 [style-guide.md](references/style-guide.md)：大白话标题、准确术语、内容集中，减少大块无意义留白，不能靠小字和装饰填满。来源、依据、制作批注放隐藏元数据/演讲者备注；影响结论的条件正常显示。

摘要、表格与底部说明引用同一份计算数据，统一单位、路径数和重复次数。单路径与多路径累计、单档与多档累计口径不同时，在表中并列对应值；先按未舍入数据求和，再统一显示精度。不得让汇总暗含表格未展示的倍数。

模型洞察与涉及模型特性的技术项目，共用 [数据与分析流程](references/source-acquisition.md)：用户材料优先，从模型结构和匹配版本的运行实现出发，分析特性作用的模块、状态、通信及场景结果，再形成同一份底稿。按需使用官方模型仓库、se-tools / model_analysis、vLLM-Ascend 和上游 vLLM；不是每次都跑全部工具。调度和缓存路径按 [运行实现分析](references/runtime-static-analysis.md) 核对 patch/覆盖。两分支只改变汇报重点，不分别编造数据或支持结论；无模型关联的项目直接用项目材料。涉及A3/A5部署判断时按 [部署分析](references/ascend-deployment-analysis.md) 分别核对场景，不把个案容量当通用硬件参数。

本地材料默认不上传。解析与渲染在本机；不把私有内容送到外部绘图、图像生成、云文档或搜索服务。用户明确授权随 Skill 推送的模板单独登记来源与 SHA256，只保存该授权版式资源，不连带上传实际报告或实验数据。

## 从反馈改进

执行宿主负责分析和模型调用，本模块负责确定性生成、检查和本地规则版本管理。不运行后台自学习服务。

- 用户反馈或已验证案例形成候选规则；优先修订已有单元，注明适用范围与证据。
- `feedback → evaluate → review → promote` 后成为下次 `plan` 实际读取的规则；未通过的候选不进入正常生成。
- 视觉变更需要实际查看渲染结果；不能用脚本通过冒充人工认可。记录是谁做了检查，不能将 Agent 检查记成用户确认。
- 可以 `rollback` 回退。新案例不能默默改动已交付的 PPT 或扩大为全局规则。

接口与状态位置见 [runtime-contract.md](references/runtime-contract.md)，演进规则见 [evolution.md](references/evolution.md)。状态、测试产物和完整报告放在项目目录，核心包不携带 `node_modules`、整份PPT或实际项目数据。

未来对接 MindIE Agent 的边界见 [mindie-integration.md](references/mindie-integration.md)；目前提供本地 JSON 接口，尚未接入它的宿主插件或知识服务。
