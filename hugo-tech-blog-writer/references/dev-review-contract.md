# 博客独立审核与 Dev 发布约定

适用于新建博客、修改既有文章，以及补充 HTML 正文、配图和图注。写作者自检、构建成功与文章可读性审核是不同步骤。

## 默认可见性

- 新建或修改文章时，在 Markdown front matter 设置 `review_status: pending`。已有 `private` 或 `withdrawn` 则保留，不能因补文、配图或审核通过解除作者的撤下状态。
- `pending` 表示默认作为 Dev 内容交付，登录后才可见；使用站点已有的灰色标题与“未审核 · 未发布”标记。不要在标题前加“Dev”，也不要用 `draft: true` 或 `hidden: true` 代替审核状态，否则可能连 Dev 也不生成。
- **可读性通过不等于授权公开。** 没有用户对该文章的明确 Public 发布指令时，即使通过，也保留 Dev 状态；“提交”“推送 main”“上线看看”默认仍是部署 Dev 内容。
- 普通写作流程不得把审核结果写入会驱动 Public 的发布清单，不得自动添加 `review_status: reviewed`、刷新旧的通过记录哈希、回填旧日期或移除审核标记来让文章公开。审核记录与公开发布决策分开保存。
- 使用 `shaojiemike.top` 现有策略时，读取目标检出的 `hooks/review_policy.py` 与 `tools/review-mode/README.md` 中相关规则。`pending` 本身不能覆盖同版本的清单通过记录；遇到这种情况，用已有的 `private` 状态确保 Dev 隔离，不篡改审核事实。不要在不支持审核隔离的旧构建上声称已经部署 Dev。
- 用户已明确要求 Public 时，必须先获得最终版本的独立审核“通过”，再按站点发布流程更新版本绑定的公开记录；无需重复索取已有授权。可读性通过不能代替事实核验或用户对内容的认可。

## 写完后必须由独立子代理验证

1. 完成正文、配图、图注、HTML 附件和作者自检，再记录本次文章及正文附件的文件清单与 SHA-256。
2. **启动未参与写作的独立子代理**，明确要求它读取并使用 `$article-readability-check`（文章可读性验证器）的 `SKILL.md`，按“检查模式”只读审稿。不能由写作者自己扮演审稿人，也不能用已有四层自检或 HTML 校验器替代。
3. 只传入文章路径、实际正文附件、必要来源上下文和目标读者；不要传入写作者的自评结论，要求它独立判断。有 `fork_turns` 选项时使用 `none`。逐篇给出结论，不能用抽样审核代表整批通过。
4. 子代理必须阅读最终正文。HTML 文章同时读取 Markdown 载体与 `.preview.html`，必要时打开页面查看图文及交互；只看导言、front matter、标题或校验脚本输出不算完成审核。对不能读取的主要正文或图表，应报告未完成及具体缺口，不能给出通过。
5. 等待真实结果：**通过 / 需精简 / 需重写**。后两种最多列三个最影响阅读的问题，用小节或短引文定位，并给出删除、合并或替换建议。没有结果、代理不可用或 Skill 缺失时，标记“未完成独立审核”，不得伪造“通过”。
6. 写作者在用户授权范围内修正问题，再让独立子代理复审变更后的完整文章。不得为通过审稿编造事实、丢掉有效证据或越过既有文章保全约束；不能修复的问题保留在 Dev 并报告，不能宣称完整审核通过。
7. 审核后如正文、摘要、图注、正文 HTML 或引用证据发生变化，包括合并冲突带来的变化，必须复审最终版本。交付前比对受审文件哈希；不以旧结论替代新版本审核。

验证器优先从当前技能目录中同级的 `article-readability-check/SKILL.md` 或本机已安装入口定位；找不到时只查已知的规范 Skill 仓库。不可把写作者的自检升级为独立审核。若配图 Skill 被主写作流程调用，只需由最外层写作流程在全部修改完成后统一安排一次独立终审；配图 Skill 单独调用时自行安排。

## 子代理任务模板

```text
你是未参与本文写作的独立审稿人。请读取并使用以下文章可读性验证器：
[article-readability-check/SKILL.md 的实际绝对路径]

只读检查下列最终文件，不修改文章、不提交、不推送、不更改 Public/Dev 状态：
[Markdown 与正文 HTML/必要图表的实际绝对路径]
目标读者：[文章目标读者；默认没有项目背景、耐心有限的入门读者]
必要来源上下文：[只给理解原文所必需的材料]

阅读实际全文后，逐篇给出“通过 / 需精简 / 需重写”之一及一句理由。
未通过时最多给出三个问题，附小节或短引文定位和具体修订建议。
关注核心理念与实际效果是否清楚，个人环境、调试与测试流水账是否掩盖主线。
保留支撑结论的必要条件和证据；不以固定字数、标题数量或关键词计数代替阅读。
声明未读到的正文或图表，不声称完成未做过的事实核查。
```

## 记录与交付

- 在任务交付记录或仓库已有的非发布型审核报告中记录：文章路径、受审版本哈希、子代理标识、所用 Skill、结论和主要未解决问题。不要把审稿过程写进文章正文，不把该记录自动导入 Public 清单。
- 构建验证应覆盖两种模式：Dev 中能访问文章及 HTML 附件；Public 的首页、搜索、标签、分类、归档、sitemap 和直接 URL 均不暴露默认 Dev 文章。只在实际完成对应验证后才声称通过。
- 交付明确说明“独立可读性审核：结论；发布状态：Dev（默认）”。未完成审核时如实说明，保留 Dev；只有实际完成 Public 发布才报告 Public。
- Git 提交、推送和部署仍遵守各 Skill 与当前用户请求的授权边界。本约定不额外授权外部发布，也不因存在缺项而要求重复确认已获授权的操作。
