# 专家表达与成果呈现

## 1. 读者与主张

默认读者熟悉本领域的模型、框架、并行计算及性能分析。文章承担技术成果交流与方案展示：优先让读者识别约束的特殊性、方法的原创或改进之处、机制成立的原因和最终收益。

采用凝练、专业、自信的语气。用技术细节和量化结果体现实力，不依靠“完美”“无懈可击”“全面领先”等自我评价。已有依据的结论直接陈述，只有尚属假设的因果关系才使用“推测”“预计”。保留定义主张范围的少量条件，不为每个判断附加长段免责说明。

## 2. 标题与措辞

优先使用“技术对象 + 机制/优化方向”的标题，标题应与实际实现范围一致。各级标题采用简洁中文技术短语；博客顶层标题若有仓库约定，遵循其格式。避免问句、开发口吻、情绪词和没有量化依据的最高级。

| 松散表述 | 专家表述示例 |
|---|---|
| 为什么这里这么慢 | GDN 关键路径与瓶颈分解 |
| 干掉多余的 transpose | 张量布局协同与转置消除 |
| 把通信藏起来 | 通算流水重叠与同步开销削减 |
| 这个坑怎么解决 | 变长序列下的分块调度设计 |
| 又快又省显存 | 激活生命周期优化与峰值显存压缩 |
| 做了很多测试，效果非常好 | 消融验证、关键指标与端到端收益 |

替换措辞前核对技术含义：“隐藏”与“消除”不同，“异步”不等于“并行”，“局部加速”不等于“整网收益”。明确对象、因果关系、指标单位及比较基线，避免“性能优化了 20%”等含糊表达。

## 3. 将开发过程提炼为实验结论

使用 **实验类别 → 技术发现 → 设计选择 → 关键结果** 压缩原始材料。写清完成了何种验证即可，不把读者带回调试现场。

| 原始材料 | 成稿处理 |
|---|---|
| PR 链接、commit、分支和源码行号 | 放在内部来源清单；正文以实现机制表述，必要的外部归属简洁引用 |
| 驱动、工具链、操作系统、安装参数 | 内部核对；只保留会改变结论的设备规模、负载、精度或执行模式 |
| 编译报错、补丁过程、反复换环境 | 通常省略；若揭示关键编译机制，直接讲机制与最终实现 |
| 逐轮打印、层层二分、完整堆栈 | 概括为“通过逐层对照/消融分析定位……”并交代技术发现 |
| 多轮参数搜索和未采用实现 | 概括搜索维度及最终选择依据，不逐一复述试验过程 |
| 普通验证脚本与命令 | 留作独立复现材料；正文归纳验证方法和主要结果 |
| 有独特设计的 Profiling 或迭代工具 | 可写特色附录，突出机制和效率成果，避免变成操作手册 |

以下仅示范语言转换，不提供新的实验事实：

- 原始叙述：“在某 commit 上编译失败，换包后打印发现索引计算触发同步，又反复采集了多个版本的 trace。”
- 成果叙述：“通过时序剖析与索引计算消融，确认重复主机同步构成关键路径开销。将分块索引预计算前移至迭代入口，使其在迭代内复用，从而降低调度开销。”
- 有实际数据时，再接局部耗时、端到端净收益及必要质量结论；没有数据时不补造效果。

## 4. 选择性展开与适当留白

文章可以集中展示已验证的核心能力和已采用方案，不要求覆盖全部功能、尝试和边界。

| 情况 | 呈现方式 |
|---|---|
| 已解决的编译/集成问题、常规 corner case | 省略，或概括为已完成相应适配；不复述故障过程 |
| 非目标场景、未采用试验、外围功能 | 允许留白，不主动增设局限性章节 |
| 重要取舍已经反映在最终净收益中 | 优先呈现净收益，仅在解释创新机制时展开成本构成 |
| 限制了结论范围的条件 | 将条件融入主张或图注，用一句话限定，例如“在长序列训练负载下……” |
| 已知问题会改变核心性能、正确性或质量结论 | 收窄主张、补必要验证或简要说明；不能删去后仍宣称无条件成立 |

“主要优化阶段”图可以省略开发中的试错节点，但保留阶段实际配置和正确的起止值；不能拼接不兼容配置制造连续增长，也不能把撤销的方案包装为最终收益来源。代表性数据要对目标场景有代表性，不能用极端最佳点替代已知整体表现。

减少内容应减少枝节，不改变事实。自研、适配、复用等贡献归属准确表述；正文不展示 PR 列表，不等于将外部成果归为原创。

## 5. 收束方式

正文优先以“核心技术贡献 + 最终耗时与加速比 + 系统价值”结束。只有用户关心后续路线或其能强化技术判断时，才补演进方向；不强制列待办、失败、风险或剩余缺口。

最后从专家视角逐段检查：删除该段后，是否仍能理解设计、相信关键结果、判断技术价值？若答案是肯定的，通常可删去或进一步压缩。保留架构、公式、关键对照实验与结果的解释深度，不把专业性误解为材料堆积。
