# 军旅类比汇报

将不同业务的研发工作映射为听众熟悉的作战概念，使其快速理解：**目标是什么、局面怎样、卡在哪里、准备怎么推进、需要什么决策、怎样确认结果。**

让每个类比携带一个具体管理判断，并能还原成原始业务事实。用中文输出；保留必要的技术名称、数据及指标口径。

## 1. 确认材料与用途

优先复用当前对话和用户提供的材料，识别以下信息：

- **用途和听众**：术语联想、口头汇报、书面材料、资源申请、风险说明或复盘；听众熟悉哪些业务和军旅表达。
- **目标和当前状态**：业务结果、阶段、已有成果、主要阻力、已知约束。
- **决策请求**：希望上级协调、批准、取舍或知悉什么。
- **事实依据**：指标、对照条件、责任人、时间、资源数量、验证结果和未知项。

材料足够时直接完成任务。缺少数值、负责人或期限时，使用“待补”或明确占位符；只有缺失信息会改变主结论或决策方向时，才提出最少的澄清问题，并继续完成可确定的部分。

用户只要求术语联想时，直接提供可选映射和示例句，不追问具体项目。将公司文化、受众经历等作为用户提供的场景背景；未经核实，不扩展成关于企业或领导个人的事实断言。

## 2. 提取管理结构

先识别业务中的因果关系，再选择军旅概念。不要逐个替换名词。

| 业务问题 | 军旅视角 | 必须保留的信息 |
|---|---|---|
| 要实现什么，为什么值得投入 | 作战目标、主攻方向、制高点 | 业务价值、优先级、范围、成功条件 |
| 当前处于什么阶段，受到哪些约束 | 态势、地形、关键隘口 | 阶段、依赖、瓶颈及其证据 |
| 谁执行，谁协同，谁能支援 | 编组、联合作战、预备队 | 责任边界、投入期限、可用能力 |
| 对问题和方案了解多少 | 侦察、试探、战场感知 | 已知事实、假设、验证方法 |
| 推进需要哪些物质和平台条件 | 弹药、装备、补给线 | 资源种类、数量、到位时间及限制 |
| 如何推进，怎样判断完成 | 战法、局部突破、巩固战果 | 具体行动、验证范围、验收标准 |

区分工作性质：探索问题先做侦察；明确的技术瓶颈组织攻坚；多团队共同交付强调协同；守住稳定性强调防线；长期平台建设强调装备、保障和梯队。根据事实组合表达，不把日常工作全部升级为会战。

## 3. 选择有解释力的映射

按需读取 [术语映射](references/analogy-map.md)。选择能够揭示问题结构的词，而非只增加气势的词。

遵循以下规则：

1. **对应具体对象**：说明“主攻方向”是什么、“弹药”具体缺什么、“结合部”位于哪两个团队或模块之间。
2. **带出管理动作**：“战线过长”对应取舍范围；“补给不足”对应保障资源；“侦察不足”对应验证；“结合部薄弱”对应接口与责任闭环。
3. **保持术语一致**：在同一份材料中，为“兵力、装备、弹药”等确定具体含义，不随段落任意漂移。
4. **保留可还原性**：首次使用重要类比时，在相邻句说明实际业务含义；跨业务听众应能理解具体障碍。
5. **控制表达密度**：默认每段围绕一个核心类比展开，再接事实和行动；用户要求加强军旅风格时可以提高密度，仍保留可核对事实。
6. **解释资源的作用**：提出加强炮火或增加兵力时，说明新增资源将解除哪个约束。若瓶颈是串行依赖、等待或重复工作，优先改通路和战法，不默认加人有效。

避免把研发人员描述成可消耗的弹药，把合作团队描述成敌军，或把技术假设失败归结为意志不足。用问题、约束和目标作为作战隐喻的对象。

## 4. 组织可直接使用的汇报

根据用户请求选择一种输出，不强制一次交付全部格式。需要模板和示例时读取 [汇报模板与示例](references/report-patterns.md)。

### 术语联想

按目标、执行、组织资源、风险成果等业务主题给出表格：

**研发事项 → 军旅抽象 → 隐含的管理判断或动作 → 可直接使用的汇报句。**

优先覆盖用户未提到的概念，避免堆砌含义重复的词。选择最有价值的几项，指出适用条件。

### 现有材料改写

先给可直接使用的汇报稿。默认使用克制、简洁的正式语气，根据需要覆盖以下顺序：

1. **目标与态势**：先说核心判断，让听众知道主攻目标和当前局面。
2. **进展与阻力**：说明已完成什么、证据是什么，以及主要障碍。
3. **推进方案**：说明下一步行动、分工、阶段目标和预计时间；区分计划与承诺。
4. **决策请求**：明确请求谁决定什么，以及资源数量、支援时长或取舍范围。
5. **验收与边界**：说明如何确认有效、尚未覆盖什么；重要风险须留在正文中。

短材料只保留必要项，不为凑结构编造事实。涉及多项术语或复杂业务时，再附简短映射说明和待补信息。用户只要求润色时，忠实改写已有内容，将新增方案单列为建议，不写成既定安排。

### 资源请求与方案比较

把“需要支持”写成具体请求：**资源是什么、投向哪里、解除什么约束、占用多久、如何确认收益。** 仅在材料支持时比较“补充资源”和“调整目标或期限”等选项；没有证据时，将效果写为待验证预期。

### 成果与复盘

分别说明取得的结果、验证范围、剩余缺口和能力沉淀。区分“局部突破”“形成交付能力”“形成可重复的建制能力”；用已验证事实确定表述强度。

## 5. 保持证据和类比边界

- 保留原始数据、单位、基线、范围和统计口径；不要删掉会改变结论的条件。
- 区分目标、估算、假设、计划和实测结果。没有时限依据时，不自行承诺“确保按期完成”。
- 对技术工作，分别标明源码分析、主机模拟、编译通过、单场景实验、真机验证、规模验证和端到端结果；不要从一种证据升级到另一种结论。
- 单个模块改善不代表整体目标达成。投入人数、人天和算力不代表已经产生业务收益。
- 允许侦察得出“此路不通”；对尚不确定的技术路线设置验证点，不直接写成必须拿下的既定阵地。
- 使用“主动转进”“收缩战线”时，明示取消、延期或改变的业务目标、实际影响和责任，避免掩盖失利。
- 不编造企业内部术语、领导原话、历史战役细节或所谓官方口径。保留用户明确要求的既有代号；无法核实的历史细节改用通用类比。
- 将参考文件中的数字和人物视为虚构示例；不得移植为用户项目事实。

## 6. 交付前检查

检查最终稿是否满足以下条件；不默认把检查清单附到汇报正文中：

- 听众能快速复述目标、进展、主要阻力和需要决定的事项。
- 每个关键军旅词都有明确的业务对应物，并有助于理解或决策。
- 数字、责任、期限和承诺来自输入；新增建议、未知项与示例均已区分。
- 风险与结果的适用范围仍然清楚，语气没有超过证据。
- 资源请求足够具体，且说明为何有助于推进；缺失项如实标注。
- 删除军旅词后，内容仍是一份清楚、准确、可执行的业务汇报。
