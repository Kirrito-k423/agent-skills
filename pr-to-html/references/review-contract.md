# 审查数据契约

`pr_to_html.py prepare` 从固定 base/head 生成审查骨架。不要手工修改以下机器字段：

- `schema_version`
- `comparison.base_sha`、`comparison.head_sha`
- `stats`
- `segments[].id`、`file`、`hunk`、`old_lines`、`new_lines`、`added`、`deleted`

允许且必须填写的字段如下。

## 总体字段

| 字段 | 要求 |
| --- | --- |
| `review.title` | 简洁说明 PR 目标 |
| `review.pr_url` | PR URL；没有则写空字符串 |
| `review.requirement` | 用户真正要求打通的功能 |
| `review.non_goals` | 明确不属于本 PR 的内容，可为空数组 |
| `review.summary` | 机制与结果概述，不得只复述文件列表 |
| `review.scope_verdict` | `最小`、`可收敛`、`明显过大` 三选一 |
| `review.scope_reason` | 用直接修改、支撑修改和越界修改的证据解释结论 |
| `review.validation_level` | `未验证`、`静态检查`、`编译`、`单元测试`、`集成测试`、`真实环境端到端` 六选一 |
| `review.recommended_actions` | 合入前的具体动作；确实无需动作时填 `[]` |

## 单元字段

每个 `segments[]` 都必须填写：

| 字段 | 要求 |
| --- | --- |
| `reviewed` | 实际复查完成后设为 `true` |
| `requirement_link` | 本单元与需求的直接关系；支撑性修改写清依赖链 |
| `old_title` | 旧行为或缺失点的短标题 |
| `old_explanation` | 旧实现做什么、为何要改；引用具体条件，不能泛称“不好” |
| `evidence` | 至少一条证据，如调用位置、类型/shape、复现、测试或规范 |
| `new_title` | 新机制的短标题 |
| `new_explanation` | 解释数据流、控制流或契约如何变化，不逐行翻译代码 |
| `correctness` | `合理`、`需修改`、`应删除` 三选一 |
| `correctness_reason` | 覆盖正常路径与关键边界；无法确认时必须判 `需修改` |
| `minimality` | `必需`、`支撑`、`疑似越界`、`应删除` 四选一 |
| `minimality_reason` | 回答能否删除、复用或缩小；说明为何必须在本 PR 中 |
| `risks` | 剩余风险；没有则填 `[]`，不得写“无”掩盖未验证项 |
| `validation` | 已执行且能约束本单元的验证；没有则填 `[]` |

脚本拒绝空文本、模板占位词、非法枚举、未复查单元、遗漏 ID 和过期 diff。

## 展开上下文的证据边界

源码上下文不属于人工审查字段，也不写入审查 JSON。`build` 必须在重新确认 base/head 与审查单元后，直接从这两个固定提交读取变更文件：

- 修改前上下文来自 `base_sha`，修改后上下文来自 `head_sha`。
- 重命名文件分别读取旧路径和新路径。
- 每个文件、每个版本只在 HTML 中嵌入一次，审查卡片通过文件名和行号按需加载。
- 当前工作树、PR 页面缓存和网络响应都不能替代固定提交中的源码。
- 二进制、提交中不存在或无法解码的文件不提供展开内容，但不得因此隐藏真实 diff。

## 解释尺度

连续增删块是机械覆盖单位，不一定等于一个完整设计决策。若一个决策跨多个单元：

- 在每个单元解释它承担的局部职责。
- 用相同的需求术语串联，不复制空泛结论。
- 在总体 `summary` 中解释组合后的端到端数据流。

纯格式化行也必须出现。将其标为 `疑似越界` 或 `应删除`，除非它是工具强制且与功能修改不可分割。

## 证据等级

优先级从高到低：

1. 用户明确要求和仓库内适用规范。
2. 生产者—消费者数据契约、公开 API、调用链和测试期望。
3. 可复现失败、真实环境运行和针对性测试。
4. 编译、静态检查和源码推理。
5. 命名、注释和 PR 描述。

低等级证据不能覆盖高等级证据。PR 自己声称“已修复”不构成验证。

## 最小性结论

- `最小`：所有单元均为 `必需` 或不可分割的 `支撑`，没有更窄的可靠实现。
- `可收敛`：主路径可用，但存在 `疑似越界`、可拆分支撑项或明显可复用实现。
- `明显过大`：存在 `应删除`，或大范围重构掩盖主路径且无法逐项证明必要性。

总评必须与单元结论一致：存在 `应删除` 时不得判 `最小`；存在 `疑似越界` 时通常不得判 `最小`，除非先修订单元结论并给出证据。
