# 需求分析方法选择

只在一种方法能够减少明确不确定性时使用它。记录方法的输入、输出、证据边界，以及为什么更轻量的方法不够。

## 选择矩阵

| 不确定性 | 优先方法 | 最小输入 | 输出 | 常见误用 |
|---|---|---|---|---|
| 谁受影响、谁决定 | 干系人地图 / RACI | 团队、系统、运行背景 | 角色—利益—影响—责任 | 把组织架构当用户证据 |
| 用户实际怎样工作 | 现场观察 / 情境调查 | 场景、用户、现行系统 | 实际流程、绕行和隐性需求 | 只听“应该怎样做” |
| 用户为什么提出该功能 | 访谈 + JTBD | 触发、任务、绕行、结果 | 场景—任务—结果陈述 | 把客户方案照抄成需求 |
| 多方边界为何不一致 | 需求工作坊 / JAD | 各方角色、争议点 | 共识、分歧、责任和待决定项 | 只有会议纪要没有结论 |
| 问题覆盖面多大 | 问卷 / 工单与日志统计 | 用户群、样本、问题分类 | 频率、群体差异和趋势 | 用问卷独立挖掘复杂根因 |
| 问题为什么发生 | 5 Whys / 问题树 | 症状和基本证据 | 原因链和待验证假设 | 强迫复杂系统只有一个根因 |
| 多个解释哪个成立 | 假设驱动分析 | 竞争假设、区分性证据 | 支持、否定和未决假设 | 收集很多数据但没有证伪条件 |
| 系统边界在哪里 | 上下文图 | 系统、参与者、外部依赖 | 控制边界和接口 | 把内部模块图当上下文 |
| 责任如何交接 | 泳道图 / BPMN | 角色、事件、交接 | 流程、职责和异常路径 | 混淆泳道与消息语义 |
| 用户与系统怎样交互 | 用例分析 | 参与者、触发、前置 | 主流程、异常、后置 | 只有 UI 正常路径 |
| 状态如何变化 | 状态机 | 对象、状态、事件、守卫 | 合法转换和终态 | 把函数调用画成状态 |
| 数据与控制怎样移动 | DFD / 时序图 / 数据血缘 | 边界、接口、顺序 | 输入、输出、所有权和依赖 | 一张图同时声称解释所有视角 |
| 目标由哪些能力组成 | 目标树 / FBS / FAST | 顶层结果、用户、边界 | 目标—能力—行为层级 | 镜像代码模块 |
| 现有技术为何不满足 | 瓶颈分析 / Profiling / 基准 | 目标场景、现有系统、指标 | 技术基线和限制 | 在环境不固定时比较数字 |
| 有哪些技术路线 | 技术扫描 / 竞品 / 代码与架构研究 | 需求、约束、评价准则 | 候选、原理、边界和成熟度 | 只列功能或只找支持推荐方案的资料 |
| 关键技术能否成立 | PoC / Spike | 会改变决策的假设 | 受控实验和判定 | 把 PoC 做成正式功能或最终验收 |
| 质量冲突如何权衡 | 质量属性场景 / ATAM 风格效用树 | 业务驱动、架构、候选 | 风险、敏感点和权衡点 | 没有需求责任人的权重打分 |
| 项目能否落地 | 六维可行性分析 | 方案、数据、资源、组织、合规 | 阻塞项、前置条件和处置 | 只判断“技术上能跑” |
| 需要多少工作量 | WBS + 类比/自下而上/三点估算 | 范围、交付物、依赖 | 区间、关键路径、置信度 | 只估核心编码或给单点人天 |
| 是否值得做 | 价值—成本—风险 / RICE / WSJF | 基线、价值、成本、风险 | 立项、延后或拒绝建议 | 用精确分数掩盖未知 |
| 哪些需求先做 | MoSCoW + 依赖分析 | 价值、依赖、工作量、风险 | 首版范围和延后理由 | 所有需求都标 Must |
| 质量怎样可验收 | 质量属性场景 | 来源、刺激、环境、响应 | 指标、阈值和验收设置 | 写“高性能、高可靠” |
| 行为怎样可验收 | Given-When-Then | 前置、触发、外部结果 | 可评审验收场景 | 断言内部变量或实现细节 |
| 决策链是否完整 | 开发前追踪矩阵 | 问题、目标、需求、方案、验收 | 双向覆盖和缺口 | 提前加入代码和测试结果 |

## 方法卡

### 访谈、观察与工作坊

- **目的：**识别用户真实任务、现行流程、绕行、影响和多方冲突。
- **输入：**用户角色、场景、工单/日志、现有流程和争议问题。
- **机制：**先问事实和具体事件，再问影响、目标和不可接受结果；将个人意见与跨角色共识分开。
- **输出：**访谈记录、观察事实、共识、分歧和待决策项。
- **边界：**表达频繁不等于覆盖面大；必须用观察、数据或多方材料交叉校验。

### 干系人地图与 JTBD

- **目的：**把功能请求还原成有人负责、可观察的用户任务。
- **输入：**触发场景、用户角色、当前绕行、期望进展和不良后果。
- **机制：**映射影响与决策权，再写成“当……时，需要……从而……同时避免……”。
- **输出：**干系人表和任务陈述。
- **边界：**不能把“接入某技术”直接写成 JTBD。

### 5 Whys、问题树与假设驱动

- **目的：**区分表面请求、症状、直接原因和系统性原因。
- **输入：**可观察问题、频率/影响材料和竞争解释。
- **机制：**建立临时因果链，在证据中断处停止；为竞争假设设计能区分它们的证据。
- **输出：**原因、被否定解释和未决假设。
- **边界：**复杂系统通常由多个因素共同作用，5 Whys 不是证明工具。

### 上下文、场景与功能分解

- **目的：**确定系统边界并把目标拆成可验证能力。
- **输入：**参与者、环境、事件、接口、生命周期和顶层目标。
- **机制：**先划边界，再描述正常/异常场景，最后按用户能力下钻到系统行为。
- **输出：**Context、用例/流程/状态/数据模型和功能树。
- **边界：**需求模型不应提前固化无必要的内部架构。

### 技术扫描、基准与 PoC

- **目的：**建立技术基线，比较候选，并降低会改变决策的关键不确定性。
- **输入：**需求、约束、现有瓶颈、候选和统一评价准则。
- **机制：**研究标准、官方资料、论文、竞品和代码；固定环境做最小区分实验。
- **输出：**候选方案、适用边界、成熟度、PoC 结论和技术决策。
- **边界：**探索结果只支持特定条件下的可行性，不能直接成为正式验收结果。

### 六维可行性分析

- **目的：**判断方案能否在现实组织和生命周期内交付。
- **输入：**技术方案、数据、资源、团队、运营和合规材料。
- **机制：**分别判断技术、数据、资源、交付、运营和合规，识别阻塞项与前置条件。
- **输出：**可行/条件可行/不可行结论和处置。
- **边界：**“原型能跑”只覆盖技术可行性的一小部分。

### WBS 与区间估算

- **目的：**得到有范围、有证据和有置信度的投入估计。
- **输入：**首版范围、交付物、依赖、相似项目和技术未知。
- **机制：**按能力拆 WBS，结合类比、自下而上和 O/M/P 三点估算，加入关键路径与风险缓冲。
- **输出：**工作量区间、工期、依赖和估算失效条件。
- **边界：**人天不等于日历时间；实际投入不能被倒填成原始估算。

### 价值—成本—风险与优先级

- **目的：**判断是否值得做，以及哪些需求先进入版本。
- **输入：**基线、价值、延迟成本、生命周期成本、风险、工作量和依赖。
- **机制：**按场景选择价值—成本—风险、RICE、WSJF 或 MoSCoW，并保留权重来源和敏感性。
- **输出：**Go/No-Go/延后/继续调研和首版范围。
- **边界：**底层能力不能只按直接用户数量评价；低置信数据不应产生高精度总分。

### 质量属性场景与 Given-When-Then

- **目的：**把模糊目标转换为可观察验收合同。
- **输入：**触发、环境、对象、系统响应、指标、阈值和责任人。
- **机制：**定义质量场景，再写面向用户或外部系统的前置—触发—结果。
- **输出：**`QR-*`、评测合同和验收场景。
- **边界：**这里只定义验收计划，不记录后续通过或失败结果。

### 开发前追踪矩阵

- **目的：**确保每条需求有来源，每个 Must 都能验收。
- **输入：**问题、场景、目标、需求、技术决策和验收场景。
- **机制：**双向连接并检查孤儿需求、孤儿决策和无验收 Must。
- **输出：**追踪矩阵与缺口清单。
- **边界：**需求分析阶段不连接已完成代码、测试结果和线上效果。
