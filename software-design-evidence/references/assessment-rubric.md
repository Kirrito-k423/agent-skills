# 软件设计与任职举证审计表

## 结论枚举

- **充分**：E2 实现证据和 E3 验证证据形成闭环，个人归属清晰。
- **部分**：有设计或实现，但缺验证、边界、归属或持续治理。
- **缺失**：没有可核验材料或关键工作未完成。
- **不适用**：有明确范围理由和残余风险，不是静默省略。
- **证据冲突**：不同来源矛盾，尚不能下结论。

## 软件建模与系统设计

- 系统边界、干系人、场景和非目标明确；
- 4+1 每个适用视图回答了关注点，且视图之间一致；
- 安全、可靠/可用、可测试、功能安全、体验和性能均有适用性结论；
- 关键原则/模式有问题、位置、权衡和验证；
- 设计元素能追踪到需求、代码和测试。

## 高性能设计

- 有负载、环境、版本、统计口径和阈值；
- 有关键路径与资源瓶颈分析；
- 有候选设计与代价；
- 有同条件 baseline/candidate 或明确写“待测”；
- 覆盖尾延迟、容量、退化和回归，不只平均值。

## 架构治理

- 腐化点有趋势或实例证据；
- 候选人组织了改进，而非只在代码评审留言；
- 规则已转成可执行门禁或周期审计；
- 改进前后可比较；
- 新违规有责任人和处理机制。

## 技术决策

- 至少有一个架构重要决定；
- 候选方案使用相同准则比较；
- 候选人具体作用和决策权清晰；
- 正面、负面和中性后果均记录；
- 选择已落实并验证，或明确仍是提议；
- 有重审触发器和可逆/回退路径。

## 硬失败

出现任一项时不得给“充分”：

- commit/文件/测试/数据路径不可访问或不存在；
- 从代码倒推出未记录的个人动机并当成事实；
- 把团队成果全部归于候选人；
- 没有 baseline 仍声称性能显著提升或无性能问题；
- 没有攻击路径和验证仍声称安全风险已消减；
- 没有故障/恢复证据仍声称高可靠或高可用；
- 将普通正确性包装为功能安全认证；
- 为凑数量虚构 GoF 模式、视图或架构治理成果；
- 文档、代码和验证互相矛盾但未披露。

## 优先级

- **P0**：可能导致安全、功能安全、数据丢失、不可恢复故障或核心结论失真的缺口；
- **P1**：阻止任职能力形成闭环的设计、实现、验证或归属缺口；
- **P2**：提升可维护、复用、表达或持续治理质量的缺口。
