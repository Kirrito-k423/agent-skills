# Demo、PoC 与基准实验合同

本文件用于把“跑一下看看”改造成可重复、可解释、能改变决策的实验。

## 四种实验的职责

| 类型 | 主问题 | 最小证据 | 常见误用 |
|---|---|---|---|
| Demo | 能否走通最小路径？ | 命令、环境、输入、输出、日志 | 用跑通宣称性能或稳定性 |
| PoC | 关键假设是否成立？ | 对照、成功阈值、失败条件 | 同时改太多变量，失败后无法归因 |
| Benchmark | 同口径下谁更好？ | 统一合同、重复测量、原始结果 | 混用硬件、精度、质量或版本 |
| Stress/Failure | 边界和恢复能力在哪里？ | 压力曲线、失败样本、恢复证据 | 只报告最好点，不记录退化与故障 |

## 实验前合同

| 字段 | 必填内容 |
|---|---|
| 实验 ID | 稳定唯一标识 |
| 决策问题 | 哪个结论会因结果改变 |
| 主假设 | 可被结果推翻的一句话 |
| Baseline/处理组 | 候选名称、版本和唯一改变因素 |
| 主响应 | 首要指标及方向 |
| 质量门槛 | 性能比较前必须满足的正确性/精度要求 |
| 控制变量 | 模型、数据、硬件、精度、并行、缓存、软件栈 |
| 干扰因素 | 温度、后台负载、网络、编译缓存、数据顺序等 |
| 预热 | 次数、时长和稳态判定 |
| 重复 | 独立运行次数和随机化顺序 |
| 测量窗口 | 起止事件、是否包含预处理/传输/后处理 |
| 统计量 | 中位数、均值、分位数、波动和置信区间 |
| 异常规则 | 超时、OOM、错误结果和异常值如何处理 |
| 资源上限 | 时间、内存、设备、API 和人民币预算 |
| 停止/回滚 | 何时中止，如何恢复环境 |
| 原始证据 | 日志、Profiler、配置、CSV/JSON 和失败样本路径 |

## 最小执行顺序

1. 记录代码提交、依赖锁、硬件和系统环境指纹。
2. 用最小输入完成正确性检查，确认两组语义等价或明确差异。
3. 冷启动与稳态分开测量，不混成一个均值。
4. 预热到指定条件后开始计时；每组做多次独立运行。
5. 若可行，随机化候选执行顺序；将机器、日期或数据批次作为区组记录。
6. 同时采集质量、时延、吞吐、内存、通信、能耗、错误和稳定性。
7. 保存每次运行的原始值，不只保存平均数。
8. 记录失败和异常样本；除非预先定义，不因“不好看”删除数据。
9. 用 Profiler 或日志解释差异来自何处，不只报告差异存在。
10. 复跑最关键条件，确认结果能在相同环境重现。

## AI/系统基准最低控制项

- **模型**：名称、提交/权重哈希、配置、Tokenizer、解码参数；
- **数据**：数据集版本、样本分布、长度分桶、随机种子、异常样本；
- **质量**：任务指标、容差、精度损失和判定脚本；
- **硬件**：型号、数量、内存、互联、NUMA、功耗/频率模式；
- **软件**：OS、驱动、固件、编译器、Runtime、框架、Kernel；
- **并行**：DP/TP/PP/EP/CP/SP、进程绑定、通信库和环境变量；
- **负载**：Batch Size、并发、到达分布、输入/输出长度、缓存命中；
- **测量**：预热、重复、计时边界、同步方式、统计量和监控开销。

任何一项不同都可能是合理的现实比较，但必须改写问题，例如从“实现 A 比 B 快”改成“系统组合 A 在配置 X 下比系统组合 B 在配置 Y 下更适合场景 Z”。

## 结果表

| 实验 ID | 候选 | 正确性/质量 | p50 | p95/p99 | 吞吐 | 峰值内存 | 通信/I/O | 能耗/成本 | 错误/波动 | 证据路径 |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|---|

结果后必须补三句话：

1. **观察**：原始数据直接显示什么；
2. **解释**：哪条代码路径、资源约束或机制可能导致该现象；
3. **边界**：结果在哪些条件变化后可能不成立。

## 实验失败也要交付

失败报告至少包含：

- 失败阶段与首个错误；
- 已验证的环境和前置条件；
- 是否可重现；
- 对技术成熟度、集成成本或文档质量的新增证据；
- 下一次最小诊断动作；
- 当前是否已经足以改变 Trial/Adopt 建议。

不要把安装失败直接等同于技术不可用，也不要把反复依赖冲突从成熟度评估中删除。
