# 64p 案例：从两个方向解释黄绿红

仅在需要理解“发得快却等得久”、串行目标顺序或分布式计数路径时读取。本例来自固定源码的布局推导；下面的耗时全部为教学模型，不是设备测量。

## 固定事实和两种身份

参考 [PR #8](https://gitcode.com/ChenDonYY/ascend_deepep/pull/8/) 中的 [固定源码](https://gitcode.com/shaojiemike/ascend_deepep/blob/00ee1c37c6e15c71373dd2b268a7df404d3cebad/kernels/elastic_dispatch.cpp)，重点查看：

- `CalAndSendCnt`，L1646–1701：分专家，逐条写count/flag，每条之后等待MTE3。
- `CalCumSum`，L1726–1747：发送、接收、前缀三个阶段及DebugClock边界。
- `WaitDispatch`，L1539–1571：轮询本核接收槽，清flag并发布局部和。
- `GetCumSum`，L1480–1536：等待本卡16核的局部和。

只有当前接口和分工仍符合以下配置时，才可代入本例：

```text
64 rank；每节点8个连续rank；全局384专家；每rank6专家
16个计数核：AIV40…55；c = AIV编号 − 40
```

发送核c负责24个全局专家，目的rank为 `[4c, 4c+3]`。目的rank r的本地专家e在发送者循环中的零基位置为：

```text
k = 6 × (r mod 4) + e
发送者核编号 = 40 + floor(r / 4)
```

目标接收槽按 `[local expert][source rank]` 排列，不能沿用发送分组：

```text
j = 64e + source
目标偏移 = 32j 字节
接收者核编号 = 40 + floor(j / 24)
```

因此目标rank60上的AIV55接收e5、source40–63；目标rank63上的AIV55也接收同一来源范围。所需计数由每个source上的AIV55发送，但它们不是目标卡上那个AIV55。

rank60上的AIV54发给56–59，虽不含自己，却全在本节点。黄色短的候选机制是目标节点局部性，而不是一个“只给自身加速”的分支。没有拓扑与逐目标时间戳时，不进一步编造链路跳数。

## 三列先这样排

| 配置与依赖身份 | 关键代码与位置 | 色块模型要解释的现象 |
|---|---|---|
| rank60/AIV55向本节点发；接收其他source上的AIV55写来的e5 | `curExpertId++` 循环中，给60的e5是第6条；前面有5轮 | 自己黄色短，材料较早到，后续更多等待落在红色。 |
| rank63/AIV55同样向本节点发；接收上述source写来的e5 | 给63的e5是第24条；前面有23轮 | 自己黄色同样短，但材料晚18轮；绿色增加、红色可能减少。 |

这里的先后只覆盖同一核负责的四个目标。rank59与60由不同的发送核负责，不能外推“全局rank越大绿色必然越长”。

## 互斥的七组示例账本

令T1为模型共同起点，假设各source同时开始。每轮τ是计数准备、发送与同步的有效合计，ℓ是从该轮起点到对端可观察的余量；两者都不是已测物理链路延迟。

```text
Y_c = P + 24τ出
A_c = max_{本核所需(source,e)} (P_source + kτ入 + ℓ)
G_c = B + max(0, A_c − Y_c − B) + C
F_c = Y_c + G_c
M = max_{本rank的16个计数核} F_c
R_c = M − F_c + D
```

| 组 | 核心代码 | 归属 | 模型成本 |
|---|---|---|---|
| ① | 输入复制、准备、SIMT计数 | 黄/橙 | P |
| ② | 24轮SetValue、S_MTE3、DataCopy、MTE3_S及发送收尾 | 黄/橙 | 24τ出 |
| ③ | SplitToCore、Reset、BufferInit | 绿 | B |
| ④ | WaitDispatch中额外等输入 | 绿 | max(0,A−Y−B) |
| ⑤ | 必需检查固定开销、清输入flag、发布局部和 | 绿 | C |
| ⑥ | GetCumSum中等本卡所需核 | 红 | M−F |
| ⑦ | 取前段和、清Q、计算P、复制并发布ready | 红 | D |

红色分组之外还有其他执行阶段；本表三色之和不是整次dispatch的全部latency。不能再把完整CalRecvAndSetFlag时间叠加到⑥⑦上。

一组**演示参数**：P=1μs、τ近=0.25μs、τ远=5.45μs、ℓ远=1.5μs、ℓ近=τ近/2、B=1μs、C=1.5μs、D=4μs。假设局部和在绿色结束即被其他核观察，忽略起步偏差和每轮争用差异。

| 配置 | 黄/橙 | 绿 | 红 | 三色之和 |
|---|---:|---:|---:|---:|
| rank60/AIV55 | 7.00 | 24.25 | 107.05 | 138.30 |
| rank63/AIV55 | 7.00 | 122.35 | 8.95 | 138.30 |

rank60本核早收齐，并不意味着本卡所有计数核都就绪：其他计数核还可能在向别的节点发送，尚未开始它们的接收阶段。本模型M=134.30μs来自全16核的推导，不是给每个对照行手填的拟合参数。

绿色差值为 `18×5.45=98.10μs`，红色反向变化同样多。这个例子展示了足够大的候选延迟来源；仅凭数量级吻合不能证明真实设备上只有这个原因。

## 两个可证伪预测

1. 只反转每个核的四个目标发送顺序、保持每目标专家升序和成本假设：rank60与63的上述绿红应交换，黄色不变。
2. 令节点内外有效每轮耗时相同，并保持输入在最后发送完成前可观察：原快核不再提前很久进入接收，额外输入等待趋于消失。若改变了可见性或起步假设，应重新计算，不能沿用结论。

真实验证需按source记录四个目标批次的发送时间、接收核最后缺失的source/expert，以及GetCumSum等待区间。不要通过给每个核添加一个无来源偏移来抹去模型残差。
